Common Error Codes

  • 400: validation failure, missing field, invalid state.
  • 401: missing, invalid, or expired token.
  • 403: role or ownership denied.
  • 404: record not found.
  • 405: method not allowed.
  • 429: rate limited OTP/login/security action.

Authentication, OTP, And Test Flows

JWT flow: register or login, store the returned access token for protected endpoints, use refresh token with refresh endpoint, logout to blacklist refresh token. JWT_SECRET is required from environment variables; there is no hard-coded fallback, and token generation fails if it is missing.

OTP flow: registration email OTP and password reset OTP are stored hashed with expiry, attempts, cooldown, and used markers. Login OTP is optional when requested by the login flow.

Authenticated password reset flow: logged-in users (family, caretaker, admin) can reset their password without knowing the old password. Call POST /api/v1/auth/request-password-reset-otp (Bearer token required, no body) to receive a 6-digit OTP at the registered email. Then call POST /api/v1/auth/reset-password-with-otp with {"otp":"123456","new_password":"NewPass123","new_password_confirm":"NewPass123"}. On success, the password is updated, all JWT sessions are blacklisted (user must re-login), and remaining OTPs are invalidated. OTPs expire in 10 minutes, enforce max 5 attempts, and respect a 60-second resend cooldown. Rate limited: 5 OTP requests and 5 verification attempts per 15 minutes per user.

Forgot password flow: Flutter should use POST /api/v1/auth/forgot-password/request-otp, then POST /api/v1/auth/forgot-password/verify-otp, then POST /api/v1/auth/forgot-password/reset. The request accepts {"login":"email / phone / username"} and always returns the generic success message for unknown accounts. OTPs are hashed in otp_verifications. Reset tokens are returned once as data.password_reset_token, stored only as hashes in password_reset_tokens, expire in 10 minutes, and are single-use. The reset request body is {"password_reset_token":"token-from-verify-step","new_password":"NewPass123","confirm_password":"NewPass123"}. Clients must never use OTP digits as the reset token.

Environment safety: Copy .env.example to .env for local or live setup. Real JWT_SECRET, SMTP app passwords, database passwords, and other secrets must never be committed. Live deployments must use APP_ENV=production and rotated secrets.

Deprecated password reset endpoints: POST /api/v1/auth/forgot_password and POST /api/v1/auth/reset_password remain only for legacy compatibility. New Flutter screens must use the three /forgot-password/* endpoints. Legacy forgot_password returns a generic success for unknown, inactive, or unverified accounts. Password rules are centralized: all registration, forgot-password reset, authenticated reset-password OTP, legacy reset, and change-password flows require at least 8 characters and return field-level validation errors.

Care requests flow: Caretaker app should use GET /api/v1/booking/caretaker_requests, GET /api/v1/booking/caretaker_request_detail?booking_id=ID, and POST /api/v1/booking/respond_request. Responses are scoped to the authenticated caretaker, use snake_case, return requests: [] plus pagination, avoid sensitive patient medical fields in lists, block duplicate responses with 409, notify the family, and write audit metadata for admin analytics.

Booking request lifecycle: request status transitions are centralized in app/services/booking_workflow. Allowed paths are pending -> accepted -> in_progress -> completed, pending -> declined, pending -> cancelled, and family-side upcoming cancellation accepted -> cancelled. Accept prepares a visit record and visit-start OTP. Decline stores structured reason code/label/note. Family/admin cancellation calculates refunds from successful payments.amount rows with 24h/12h tiers, so partial payments refund only the successful paid amount. Payable refunds create one pending booking_refunds row per booking and cancellation responses expose paid_amount, refund_eligible, refund_percentage, refund_amount, refund_status, and refund_record_created. Caretaker cancellation is limited to accepted future bookings, gives the family a 100% refund from successful payments, creates or reuses a replacement ticket, and notifies admins/support.

Flutter response contract: Caretaker request APIs always return {success, message, data, errors}. Validation failures use message="Validation failed" and field arrays such as {"booking_id":["Booking id must be an integer"]}. Lists return requests: [] and pagination; booleans are JSON booleans, IDs are integers, amounts are numbers, arrays are never null, and timestamps such as created_at/responded_at are ISO8601.

Response and logging policy: APIs use the standard {success,message,data,errors} envelope. Validation errors use 400, auth failures 401, permission/ownership failures 403, missing records 404, state conflicts 409, and server failures 500 without raw exception text. Production responses must not expose OTPs except family-owned visit-start OTP, JWT secrets, passwords, SMTP settings, raw gateway payloads, or internal traces.

Admin SOS list: GET /api/v1/sos/admin_sos_list accepts status=all, status=open, and status=resolved. Omitted or empty status is treated as all. Dashboard cards should pass status=open when only active SOS alerts are required. Responses keep legacy username, email, and role fields and add display aliases such as sos_id, alert_id, reporter_name, reporter_username, reporter_role, reporter_phone, booking_id, formatted_booking_id, patient_name, family_name, caretaker_user_id, caretaker_name, caregiver_name, caretaker_phone, caregiver_phone, caretaker_email, location_text, and triggered_at. If an SOS row has no direct booking_id and the reporter is a caretaker with an active visit, admin SOS responses derive booking context from existing booking ownership.

Admin Active Visits: GET /api/v1/admin/bookings?status=in_progress returns display-ready fields for active visit monitoring, including booking_id, formatted_booking_id, patient_name, family_name, family_phone, caretaker_name, caregiver_name, caretaker_phone, caretaker_email, city, address, visit_id, visit_status, checked_in_at, checked_out_at, duration_hours, active_sos_count, and latest_sos_status.

Booking status enum: pending, accepted, in_progress, completed, declined, cancelled. Decline reason enum: not_available, location_too_far, not_comfortable_with_care, personal_reasons, other. Possible error codes: 400 validation, 401 missing/expired/invalid token, 403 wrong role, 404 request not found, 405 method not allowed, 409 duplicate or invalid transition, 500 controlled server failure.

Registration flow: new accounts are first stored in pending_users, not users. The canonical flow is POST /api/v1/auth/register -> save pending registration -> send OTP -> POST /api/v1/auth/verify-register-otp -> create verified users row and role profile. Existing register_patient, register_caretaker, verify_email, and resend_email_otp remain backward-compatible wrappers around this flow.

Patient profile rule: each family account can create only one patient profile. POST /api/v1/patient/add_patient returns 409 with errors.patient when a profile already exists. Flutter should use POST /api/v1/patient/update_patient to edit the existing profile. GET /api/v1/patient/list_patients returns at most one item.

Visit-start OTP: caretaker accepts booking, family app calls POST /api/v1/booking/visit_otp to display a newly generated OTP, caretaker verifies it with POST /api/v1/visit/verify_start_otp, then checks in with POST /api/v1/visit/check_in. This endpoint is family-only, scopes the booking to the owning family user, and returns the plaintext visit_start_otp only once to that owner. OTPs are stored hashed, expire, enforce attempts, and check-in requires the latest OTP row to be verified. Notification text must never contain the OTP value.

Active visit Flutter flow: GET /api/v1/dashboard/caretaker_dashboard returns summary, active_visit, and upcoming_visits. GET /api/v1/visit/view_visit?booking_id=55 returns patient name, age, condition, contact phone, address, coordinates, visit time, care tasks, instructions, and action flags. Late arrival is not blocked by backend time rules while status remains accepted.

Family flow: register, verify email, login, add patient, list caretakers, create booking, pay advance, view active booking, manage checklist, view visit, pay remaining, review or complain.

Caretaker flow: register, verify email, login, complete profile, upload documents, wait for admin approval, accept booking, verify visit OTP, check in, update checklist, check out.

Admin flow: login, dashboard, verify caretakers, list users/bookings, monitor SOS, resolve complaints/replacement tickets, manage payouts, review audit logs.

Environment: configure .env with required JWT_SECRET and SMTP values. Do not expose real secrets in documentation, Git, Postman exports, or screenshots.

Username rules: usernames are normalized to lowercase and must be globally unique across users and non-expired pending_users, 3-30 characters, using only letters, numbers, underscore _, and dot .. Spaces and symbols are rejected. Duplicate errors return Username already taken with errors.username.

Database tables summary: users, family_profiles, caretaker_profiles, patients, bookings, booking_refunds, visit_tracking, payments, reviews, notifications, sos_alerts, documents, otp_codes, booking_checklist_tasks, complaints, replacement_tickets, caretaker_payouts, caretaker_payout_items, admin_audit_logs, rate_limits, pricing_tiers.

Pricing tiers: admins manage reusable pricing tiers through GET /api/v1/admin/pricing_tiers, POST /api/v1/admin/create_pricing_tier, POST /api/v1/admin/update_pricing_tier, POST|DELETE /api/v1/admin/delete_pricing_tier, and GET /api/v1/admin/pricing_tier_detail?id=1. Tier writes calculate platform_commission_hourly and commission_percentage from customer/caretaker hourly rates. Deleting a tier is a soft deactivate.

Caretaker approval pricing: POST /api/v1/admin/approve_caretaker now requires pricing_tier_id. With pricing_override_enabled=false, tier rates are copied to caretaker_profiles. With override enabled, admin-provided customer_hourly_rate and caretaker_hourly_rate are validated and copied while retaining the selected tier reference. Already-approved caretakers can be changed for future bookings through POST /api/v1/admin/update_caretaker_pricing.

Pricing snapshots: admin approval controls caretaker pricing with pricing_tier_id, pricing_tier, skill_level, customer_hourly_rate, caretaker_hourly_rate, and commission_percentage. New bookings snapshot the copied caretaker profile rates, total hours, customer total, caretaker earning, and platform commission. Editing a tier does not alter existing caretakers or bookings unless admin explicitly reassigns that caretaker.

Financial visibility: family APIs expose only customer-facing totals and service pricing. Caretaker APIs expose assigned tier and caretaker earning/rate, but hide platform commission and commission percentage. Admin booking and earnings APIs expose the full customer amount, caretaker share, platform commission, payout status, completed_at, and payout_hold_until.

Caretaker earnings: caretaker app earnings are read-only payout status views. Manual withdrawals are not supported. New caretaker endpoints expose Ready for Payout, On Hold, Paid Earnings, Disputed Earnings, Next Payout Date, and recent booking-wise earnings. They use bookings.caretaker_earning_amount only and hide customer totals and platform commission.

Caretaker availability: approved caretakers default to unavailable until they toggle on in the caretaker app. Family discovery shows only active, approved, available caretakers. Booking creation rejects inactive, unapproved, unavailable, or actively checked-in caretakers. Admin can still view unavailable caretakers and deactivation/rejection forces availability off.

Weekly payout rules: completed bookings enter payout_status=hold for 24 hours. Admin refresh moves only clean completed bookings to ready_for_payout; complaints, SOS/incidents, pending checklist tasks, refunds, cancelled bookings, and already-paid bookings are excluded. Weekly payout batches pay bookings.caretaker_earning_amount only, never the full customer booking amount. Payout tabs: Ready to Pay, Under Review / Hold, Disputed, Paid History.

Payment safety: POST /api/v1/payment/pay_advance and POST /api/v1/payment/pay_remaining do not accept client-submitted amounts. They calculate from immutable customer snapshot pricing (bookings.total_customer_amount, with total_amount fallback for older bookings), lock the booking row with SELECT ... FOR UPDATE, block duplicate payment attempts with 409, and hide caretaker earning/platform commission fields from family responses. Payment methods are normalized to card, upi, netbanking, wallet, cash, insurance, or other. Remaining payment is allowed only for confirmed, caretaker_arrived, in_progress, or completed bookings and is blocked for cancelled, declined, disputed, refunded, failed, unpaid-advance, already-paid, or corrupted money states. Payment rows include future gateway verification fields: gateway_transaction_reference, gateway_response_json, verification_status, verified_at, failure_reason, and idempotency_key.

Transactional notifications: The backend automatically creates typed DB notifications for booking created/accepted/declined, visit started/completed, SOS created, caretaker approval/rejection, payout paid, complaint updates, replacement updates, and OTP generation. Manual admin notifications are reserved for announcements. Notification rows include type, related_type, related_id, and metadata so Flutter can navigate to the correct screen. Device token APIs are available for future FCM push; DB notifications remain the source of truth.

Upload security: profile pictures, caretaker documents, and complaint proof uploads validate MIME type and file size, use randomized server filenames, and create upload directories with non-world-writable permissions. Uploads remain multipart/form-data only for file fields.

Latest audit: FastAPI lint and available HTTP fixture tests passed on 2026-05-17. CORS preflight is handled globally through app/services/response. JWT_SECRET must be configured in environment; there is no hard-coded secret fallback. Remaining manual verification is recommended for legacy endpoints that still have minimal date/time and numeric ID semantic validation.

Admin Caretaker List And Detail Contract

GET /api/v1/admin/users?role=caretaker and GET /api/v1/admin/view_caretaker?user_id=ID use the same normalized caretaker payload for the Admin Caregivers table and detail modal.

Shared fields include caretaker_id, full_name, phone, city, gender, dob, experience, specialization, pricing_tier_id, pricing_tier, pricing_tier_label, customer/caretaker rate fields, platform_commission_percentage, average_rating, and rating_count. Unrated caretakers return average_rating=null and rating_count=0; missing city and experience stay null.

Availability separates current state from control source. availability_status is available, unavailable, busy, or offline. availability_source is caretaker_manual, admin_override, or system_active_visit. Admin overrides expose admin_locked=1; caretaker control exposes manual_preference=on|off.

Caretaker detail keeps the legacy documents list and adds null-safe document_map keys: id_proof_front, id_proof_back, training_certificate, experience_proof, and police_verification. Each slot has id, document_id, document_type, display_name, uploaded, status, admin_note, rejection_reason, can_reupload, uploaded_at, and a bearer-protected view_url when a file exists. Stored aliases such as certificate, experience_document, and non_criminal_certificate still map into canonical slots. users.is_verified is OTP/email verification only; caretaker document/admin status uses caretaker_profiles.verification_status and document status fields.

Manual Refund APIs

Refund policy: cancelled paid upcoming bookings use successful rows from payments, not booking totals. Family cancellation gives 100% refund at 24+ hours before visit start, 50% refund at 12-24 hours, and 0% refund under 12 hours. Caretaker-side cancellation gives 100% refund before visit start. This is a prototype/manual admin refund flow; no Razorpay/Stripe refund API is called.

Refund status enum: pending, approved, rejected, processed, failed. A payable refund creates one booking_refunds row per booking and starts as pending.

Family tracking: GET /api/v1/payment/my_refunds?status=all&page=1&limit=50 lists only the authenticated family user's refunds. GET /api/v1/payment/refund_detail?id=1 returns one owned refund with patient name, caretaker name, booking date/time, paid amount, refund amount, refund percentage, method, transaction id, status, reason, admin note, and timestamps.

Admin refund workflow: GET /api/v1/admin/refunds lists refunds with filters and summary totals. GET /api/v1/admin/refund_detail?id=1 shows full detail. POST /api/v1/admin/approve_refund approves pending refunds. POST /api/v1/admin/reject_refund rejects pending refunds. POST /api/v1/admin/mark_refund_processed marks approved refunds as manually processed with refund_method and refund_transaction_id.

Bulk Caretaker Document Upload API

POST /api/v1/caretaker/upload_documents: Caretaker-only multipart upload endpoint for Flutter verification onboarding. Uploads all required documents in one request while keeping the older /api/v1/caretaker/upload_document endpoint available.

Request format: multipart/form-data only. Required Postman Body -> form-data fields: id_proof_front, id_proof_back, training_certificate, and police_verification -> File. Optional field: experience_proof -> File. Older clients may send certificate for training and non_criminal_certificate for police verification.

Validation: the four required fields must be present. experience_proof may be omitted; when provided it uses the same validation rules. Allowed MIME types are application/pdf, image/jpeg, and image/png, max file size is 5MB each, and empty/corrupted uploads are rejected.

Storage: files are saved under uploads/caretaker_docs/ using randomized filenames. The response returns relative paths and protected View API URLs. If the caretaker reuploads the same canonical document type or an older alias, the latest row is updated and the old file path is replaced after the database transaction commits.

Rejected document reupload: upload_document updates/replaces the existing row for that document type, resets status to pending, and clears admin_note/rejection_reason. upload_documents does the same in bulk and resets status to uploaded.

Failure handling: the endpoint creates and checks the upload directory, detects MIME using finfo_file(), rolls back the document transaction and removes newly moved files if any document write fails, and logs failures with the [upload_documents] prefix. With APP_DEBUG=true, HTTP 500 includes the actual exception in errors.server; production keeps a generic server error. Older databases need the documents.created_at migration before bulk upload schema validation passes.

Admin Patient Profile API

GET /api/v1/admin/patient_profile?family_user_id=312: Admin-only. Returns the patient profile from patient_details for a family user.

Behavior: validates the admin token, validates family_user_id, confirms the user exists with role family, then returns the matching patient profile. If none exists, returns success=true, message="No patient profile found", and data=null.

Response fields: id, family_user_id, patient_name, age, gender, medical_condition, allergies, medications, special_instructions, mobility_status, care_type, created_at, updated_at.

Errors: 400 invalid family_user_id, 403 admin only, 404 family user not found, 405 method not allowed.

Admin Availability Override API

POST /api/v1/admin/set_caretaker_availability: Admin-only. Force caretaker availability on/off with optional lock and audit note.

Request Body (JSON): {"caretaker_user_id": 12, "is_available": false, "lock_availability": true, "reason": "suspended_pending_review", "note": "Under investigation"}

Fields: caretaker_user_id (required), is_available (required boolean), lock_availability (optional boolean, default false), reason (optional string), note (optional string).

Lock behavior: When lock_availability=true, caretaker cannot toggle availability until admin unlocks. Lock state persists across visits.

Response: {"success": true, "message": "Admin availability override applied", "data": {"is_available": false, "availability_locked_by_admin": true, "availability_reason": "admin_forced_off", ...}}

Errors: 400 if caretaker not found or invalid params, 401/403 for auth/role, 405 method not allowed.

Availability Hardening System

Lifecycle: manual_on -> booking accepted -> check-in (on_visit) -> check-out (auto-restore to manual_on if preference ON and no admin lock).

Reason ENUM: manual_off, manual_on, on_visit, inactive, pending_review, rejected, admin_forced_off, admin_forced_on.

Expanded responses: Dashboard, availability_status, and admin view_caretaker now return: availability_reason, has_active_visit, availability_locked_by_admin, manual_availability_enabled, can_accept_booking.

Family listing: Supports ?online_only=true (15-min threshold). Sorts by recently active, rating, reviews. Family users see is_online but NOT admin reasons or last_active_at.

Booking protection: create_booking uses SELECT ... FOR UPDATE on caretaker row to prevent race conditions.

Admin users filters: ?online_only=true, ?active_visit=true, ?admin_locked=true, ?availability_reason=on_visit.

Presence tracking: last_active_at updated on: dashboard, profile, availability_status, caretaker_requests, accept_booking, list_caretaker, check_in, check_out.
